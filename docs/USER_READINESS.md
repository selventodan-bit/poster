# Poster 2.0: результаты подготовки к пользовательским испытаниям

Этот отчёт фиксирует этап до коммита `4cdc667` (Recorder и сервисный Windows E2E).
Актуальное единое Windows-приложение с `Poster.exe`, GUI-очередью и настоящим
OS mouse/keyboard E2E описано в [WINDOWS_DESKTOP.md](WINDOWS_DESKTOP.md).
Прежние ограничения CMS ниже сохраняются; прежняя инструкция с Python/CMD
не является инструкцией установки нового portable-пакета.

Работа выполнена в существующей ветке `codex/poster-2-recognition`, PR №2.
Итог конкретного коммита подтверждают [проверки PR](https://github.com/selventodan-bit/poster/pull/2/checks).
Windows ZIP и его SHA256 публикуются artifact `poster-windows` каждого запуска Actions.
Наличие artifact само по себе не подтверждает прохождение зависимых Windows-заданий.
Ссылку на проверенный запуск и точный SHA256 см. в отчёте PR.

Детектор не угадывает назначение произвольной формы без заголовка: нужен технический
сигнал reply/comment либо явный выбор типа пользователем. Edit/delete/settings не
становятся публикациями от выбора типа. Дополнительные обязательные значения
оператор вводит в браузере, затем повторяет распознавание.

Не подтвердились общие предположения о поломке YAML v1, READY, старых ключей,
SQLite-миграции, Drive, hot reload и автономного Runtime: соответствующие
регрессии проходят. Это не аудит любых внешних серверов и не живая проверка Drive.
Сохранённый READY-проект не перезаписывается; повреждённые манифесты и правила
отклоняются прежними проверками.

## B. Windows

Матрица Windows Actions: Python 3.11 / 3.12 / 3.13. На каждом runner:

1. Проверка SHA256 и распаковка ZIP в чистую папку `Poster Проверка с пробелами`.
2. Настоящий `start_recorder.cmd --check`: создание venv, установка зависимостей,
   установка Chromium в изначально отсутствующий каталог и реальный запуск браузера.
3. Повторный запуск существующего окружения, восстановление удалённой установки,
   понятная ошибка при неверном явно заданном Chromium.
4. Настоящие localhost-публикации через RecognitionSession: Browser → permalink и
   содержимое → HTTP-кандидат → закрытие Chromium → отдельный HTTP → HTTP_VERIFIED.
5. Экспорт, закрытие Recorder и KnowledgeBase; новый процесс загружает проект и
   знания, публикует через Runtime и не импортирует Playwright.
6. Отдельная настоящая инициализация Tk, русский буфер обмена и проверки состояний.

Это **сервисный E2E на Windows плюс отдельные GUI-проверки**, а не автоматизация
всего пользовательского пути мышью через GUI. Linux-проверка прав доступа не
заменяет испытание произвольных Windows ACL: ошибки записи обрабатываются,
пользователю нужна доступная для записи папка. Ремонт несовместимой версии venv
проверяется контролируемым тестом; восстановление старой установки — настоящим CMD.

Начало работы описано в [WINDOWS_README.txt](../WINDOWS_README.txt) и
[windows_quickstart.md](windows_quickstart.md). 64-разрядный Python с pip и Tcl/Tk для Windows 10/11 x64 устанавливается
заранее. Git, Docker и ручное редактирование Python/YAML для Recorder не нужны.

Первые полностью локальные проверки после распаковки:

```powershell
.\start_recorder.cmd --check
.\.venv\Scripts\python.exe scripts\check_windows_e2e.py --output .poster\first-check
```

Вторая команда создаёт три записи только на временном localhost-сайте и сохраняет
безопасный `.poster\first-check\report.json`. Повтор используйте с новым каталогом.

Неподтверждённые CMS остаются целями проекта. Значение `engine=unknown` не запрещает
универсальное распознавание: независимые положительные E2E используют неизвестный
движок, неизвестные имена и классы. Коммерческие пакеты и CAPTCHA не обходились.

MyBB A→B: на одной контролируемой паре cold learner получает LEARNING_REQUIRED,
обученный — HTTP_CANDIDATE с 1 операцией и 2 свежими привязками; затем проходит
отдельный HTTP и загруженный проект. Это **0/1 → 1/1**, не универсальный процент
распознавания. Детали изменения источника токена: [VALIDATION_REAL_CMS.md](VALIDATION_REAL_CMS.md).

Оригинальные TinyMCE 7.9.1, CKEditor 4.22.1, Quill 2.0.3, Tiptap 2.27.2 и Summernote
0.9.1 проверяются сервером: Unicode, буквальная разметка и переносы строк. 5/5.
Оригинальный лицензированный Froala не предоставлен; совместимый адаптер не
считается доказательством его оригинального E2E.

## D. Автоматические проверки и ограничения

Локальный полный прогон после исправлений launcher и Tcl: **176 passed**, включая Tk под Xvfb. Старый код отдельно воспроизвёл аварийное закрытие Tcl; отдельный процесс с исправлением проходит ту же проверку.
Ruff lint и format проходят. Точное состояние финального GitHub-коммита смотрите
в проверках PR; промежуточные красные запуски сохраняются в истории.
Два ноутбука и исходная CMS-матрица имеют воспроизводимые команды в предыдущем
[полном отчёте](VALIDATION_REAL_CMS.md); результаты нового notebook-прогона отмечены в PR.

Независимый новый набор: 9 положительных структур (тема, ответ, комментарий, AJAX,
фоновые таймеры, синхронный autosave, меню/иконки, listener-only и SPA с вложенной панелью инструментов) проходят три
публикации Browser/HTTP/Runtime в новом процессе. Отдельно проверены неоднозначные
кнопки, edit-форма, отложенный первый запрос, подмена текста перед POST, кнопка форматирования с автосохранением, CDN, обязательное поле, отмена и журнал.
Серверы учитывают все POST; никаких фоновых публикаций в положительных случаях.

Контрольный старый `negative-background`, где обработчик сначала пытается сделать
посторонний POST и только после его ошибки продолжает через await, теперь безопасно
останавливается. Не выдаём это за успешную публикацию. Произвольный асинхронный
обработчик без доказанной связи, endpoint или свежего токена требует ручного
обучения/адаптера. Задержка сама по себе разрешением на запись не является.

Все записи только на контролируемых loopback-установках. В artifacts идут исходный
Windows ZIP, SHA256 и безопасные JSON-отчёты; .poster, реальные базы, ключи, cookies,
профили и node_modules исключены. Не копируйте собственную .poster другим людям.
Отмена запроса не отменяет работу сервера: после UNKNOWN проверяйте сайт вручную.
Автоматического повтора в этой сессии и в HTTP Engine нет.

Остаются P2: закрытый Shadow DOM, чужой origin/SSO, необычная криптография JavaScript,
файлы и сложные массивы, незнакомые обязательные поля/плагины, непроверенные версии
CMS, недоступные лицензированные стенды. Живой Drive и размещённые Colab/Molab
не выдаются за проверенные по локальным тестам. Эти ограничения не расширяют
право на изменяющие запросы и не делают неизвестный workflow HTTP_VERIFIED.
