# Poster 3.0 — 4B.2: расписания и мониторинг

Продолжение Dispatcher 4A/4B.1 от `4bdc96e587ea9a104c78198b8b13e6d285955bed`.
Это локальная программа текущего пользователя, не SCM-служба и не remote API.

## Создать расписание

1. Распакуйте **весь** Full `poster-maker-windows.zip` из artifact
   `poster-maker-windows` нужного Actions run. Сверьте внутренний ZIP с
   `poster-maker-windows.sha256`. Сохраните `_internal` и `BUILD_INFO.json` рядом
   с EXE. Python на компьютере пользователя не требуется.
2. Откройте `PosterDispatcher.exe`, добавьте сохранённый граф Maker в каталог.
3. Во вкладке **Расписание** нажмите **Создать…**. Выберите проект; форма
   показывает полный SHA закрепляемого immutable snapshot.
4. Выберите однократный, интервальный, ежедневный или еженедельный режим.
   Укажите IANA timezone (например, `Europe/Moscow`), местную дату начала
   `YYYY-MM-DD HH:MM:SS`, календарное время `HH:MM:SS`, дни недели либо
   интервал в секундах. Интервал — от одной секунды до года, timeout — до суток.
   Предпросмотр запрашивается у Service и показывает ближайшие UTC/местные события.
5. Выберите политику пропусков. По умолчанию устаревшие события пропускаются,
   допустимое опоздание — 60 секунд. Нулевой допуск требует попадания точно в
   секунду; для обычной работы разумен ненулевой допуск.
6. Нажмите **Сохранить**, задайте входы через прежнюю форму 4B.1 и подтвердите.
   Служба запускает существующее обслуживание очереди. Закрывать GUI можно.

SecretRef, отдельный ключ Maker, типы JSON и выбранный snapshot профиля сохраняются
по контракту 4B.1. Входы и project key зашифрованы ключом очереди; повторный ввод
после каждого запуска не нужен. Список/preview/history не возвращают шифротекст
входов или их значения. `results.enc` не расшифровывается для мониторинга.
Секреты не следует намеренно записывать графом в открытые output-файлы.

## Изменить, отключить, удалить, обновить проект

Выберите строку расписания (действия применяются к первой выбранной строке).

- **Изменить…** меняет только время/политику, сохраняя snapshot и защищённые входы.
  Новый курсор вычисляется после времени редактирования. Старая история остаётся.
- **Пауза** запрещает новые постановки, **Включить** разрешает их снова.
  Это не отменяет уже принятые задания; отмена доступна в общей очереди.
- **Удалить** требует подтверждения и сохраняет tombstone, историю, jobs и outputs.
  Удалённое расписание исчезает из списка. История остаётся в SQLite и доступна
  через `schedule_history` по его прежнему ID.
- Для новой версии сначала явно добавьте обновлённый исходник в каталог, затем
  **Обновить версию…**. GUI показывает старый и новый SHA и требует подтверждения.
  Service проверяет snapshot, идентичность проекта и совместимость входов.
  Сохранённый snapshot выбранного профиля остаётся закреплённым.
  Простое изменение/удаление файла Maker не меняет расписание.
- Ручная кнопка **В очередь** создаёт независимое задание и не сдвигает расписание.

Поиск по проекту/ID, фильтр состояния, сортировка по названию/версии/следующему
времени и страницы по 200 строк работают через Service. Выделение сохраняется
при обновлении. Двойной щелчок либо **История расписания** показывает planned UTC,
число пропусков, job ID, результат, PID и безопасный код. Кнопки истории листают
страницы по 200 событий. Группы MISSED показывают диапазон через `through_due`
в durable history; не создаются тысячи отдельных строк пропусков.

## Время, простой и DST

Абсолютные секунды и курсоры хранятся в UTC. Однократное время задаётся в выбранной
зоне. Календарные события используют wall clock этой зоны; интервалы отсчитывают
фиксированные UTC секунды от начала и не дрейфуют после рестарта.

При осеннем повторяющемся местном времени исполняется **первая** occurrence
(`fold=0`); второй запуск в повторном часе не создаётся. Несуществующее ежедневное
или еженедельное время весеннего перехода **пропускается**, без сдвига на час.
Форма отклоняет несуществующую местную дату начала. В Windows база IANA `tzdata`
включена в общий frozen runtime; системная база timezone не требуется.

После выключенного компьютера/остановленной службы Scheduler читает прежний
курсор. По умолчанию просроченные слоты отмечаются MISSED; из слотов в пределах
допуска ставится максимум один, самый поздний. Политика **Догнать только одно
последнее событие** допускает один самый поздний слот даже за пределами допуска.
Все более старые слоты сворачиваются в одну запись с точным счётчиком и диапазоном.
Догоняющего цикла с тысячами POST одного расписания нет. Отключённое расписание
не проверяется; при повторном включении действует выбранная политика пропусков.

## Аварии и неопределённые результаты

`schedules` и `schedule_events` находятся в **dispatcher.sqlite**, schema v2.
Миграция v1→v2 транзакционная, additive и сохраняет старые jobs/executions/events.
Старая `.poster/state.sqlite` HTTP Engine не открывается и не мигрируется.

Идентичность события — SHA256(`schedule_id:due_utc_seconds`). В одном SQLite
`BEGIN IMMEDIATE` выполняются существующий deduplicated enqueue, INSERT события
с UNIQUE(schedule_id,due) и обновление next_due. Дедуп-ключ jobs включает identity
события. Авария до COMMIT откатывает всё; после COMMIT повторная admission не
создаёт второе задание. Проверены abrupt `os._exit` внутри enqueue и конкурентные
соединения, включая повтор после изменения часов назад.

Это гарантия отсутствия двойного admission, **не exactly-once для внешнего сайта**.
Для worker остаются прежние permit handshake, immutable snapshots, отдельные
OS-процессы, Windows Job Objects, timeouts, cancellation и recovery. Возможный
внешний эффект после потери Service/worker остаётся UNKNOWN, без автоматического
повтора. Неопределённые задания не переводятся планировщиком в другой статус.

Любой не подтверждённый вручную UNKNOWN/REVIEW_REQUIRED этого project ID, включая
ручное задание, блокирует дальнейшие автоматические постановки всех его версий.
Уже ожидающие плановые jobs тоже не получают worker до проверки. Ручная очередь
сохраняет прежние правила. Изучите фактическое внешнее состояние и историю, затем
нажмите **Проверено: возобновить** с подтверждением. Это сохраняет отдельную отметку
ручной проверки, оставляя исходные UNKNOWN/REVIEW_REQUIRED неизменными. Новый
неопределённый job снова блокирует проект. Потеря ключа или повреждение snapshot
приостанавливает admission с KEY_INVALID/SNAPSHOT_INVALID до исправления и явного
возобновления; повреждённые данные не заменяются новым ключом/снимком молча.

Ручные и плановые jobs используют одну FIFO по `created`, общие max_workers и
max_per_project. Приоритет одного источника не добавляется. За один tick
обрабатывается до 100 due schedules, с интервалом polling 0.5 секунды. GraphRunner
не запускается ни в GUI, ни в calendar timer: только прежним WorkerProcess.

## Служба без окна и автозапуск Windows

Служба — отдельный процесс текущего пользователя. Закрытие GUI не вызывает stop,
cancel или закрытие worker Job Object. Сохранение расписания запускает обслуживание;
при следующем старте Host наличие включённых расписаний автоматически включает
тот же singleton Dispatcher. **Остановить приём** останавливает обслуживание до
явного старта или следующего перезапуска Host.

Windows **Включить при входе…** требует явного согласия. Создаётся задача Windows
Task Scheduler с LogonTrigger текущего SID, InteractiveToken, LeastPrivilege и
`PosterService.exe --workspace ...`. Нет пароля, администратора или SCM. Путь к
EXE проверяется по BUILD_INFO/SHA256. Название задачи зависит от SID/workspace;
повторный запуск защищён прежними host/Dispatcher locks, второго scheduler нет.

**Проверить автозапуск** читает реальную задачу ОС; **Отключить автозапуск** удаляет
её. Реальные ошибки регистрации/доступа возвращаются как AUTOSTART_FAILED без
вывода stderr/приватных данных. После перемещения программы остановите прежнюю
службу и включите автозапуск из нового приложения заново: прежняя задача должна
быть обновлена на новый путь. Статус обнаруживает несовпадение пути. Если Windows
политикой запрещает пользовательские задачи, автозапуск не считается включённым.
Работа требует включённого компьютера и вошедшего пользователя; wake/boot без
login и Windows SCM не реализованы.

Linux не импортирует Windows runtime API для headless workflow:
`python -m poster.dispatcher.host --workspace <private-directory>`.
Для разработки: `uv sync --frozen --extra dev --extra maker --extra recorder`,
затем `.venv/bin/python -m poster.dispatcher.qt_app` (нужен desktop/display).

## Мониторинг и сохранность данных

Общий dashboard показывает counts всех состояний. В jobs добавлены PID,
длительность, последний подтверждённый кубик, безопасный код ошибки, planned/actual
start, ID расписания и следующий запуск проекта. SQL использует bounded pages,
индексы и grouped joins; нет RPC/SQL запроса для каждой строки Qt.
Все IPC обращения выполняются вне GUI thread через прежний authenticated JSON
transport (AF_PIPE/AF_UNIX), без pickle или нового TCP listener.

Перед обновлением завершите службу и сохраните **всю** пользовательскую папку
`%LOCALAPPDATA%/Poster/Dispatcher` (или явно выбранный workspace), включая
`dispatcher.sqlite`, `.data`, `catalog.enc`, `queue.key` и IPC key. Не переносите
только SQLite без ключей/snapshots. EXE можно обновлять отдельно от state.
Не публикуйте эту папку, session profiles или полные workdir как CI artifact.

## Проверки и границы доказательств

Новые управляемые source-тесты проверяют четыре режима, UTC/разные зоны/DST,
редактирование/пиннинг, миграцию, пропуски и bounded catch-up, параллельную admission,
настоящий abrupt crash, ограничения общей очереди, UNKNOWN/review, ciphertext и
snapshot corruption, SecretRef/типизированные секреты между реальными запусками.
Qt-тест 4B.1 расширен реальным созданием расписания через форму, закрытием окна,
реальным worker/output и повторным открытием истории.

CI сохраняет прежние **26** jobs без удаления/изменения их определений. Добавлены
2 source jobs (Ubuntu/Windows) и 1 frozen Windows job: итого **29**, без новых skips
или continue-on-error. Сам по себе этот файл не подтверждает их успешный запуск.

`scripts/check_scheduler_windows_gui.py` использует распакованный Full ZIP,
ShellExecute с PATH только Windows, mouse/keyboard/native file dialog, ввод
защищённого параметра, закрытие окна до срока, реальный packaged worker и output,
историю, перезапуск Service, отсутствие дубля, отключённый interval и ручную очередь.
`scripts/check_scheduler_windows_autostart.py` отдельно регистрирует временную
задачу с уникальным workspace, запускает её, проверяет frozen service/singleton и
удаляет задачу в finally. Отчёты/скриншоты — artifact `scheduler-windows-frozen`.
Harness имеет Python; проверяется отсутствие зависимости самого приложения от
Python в PATH. Чистая Windows VM без Python этим не подменяется.

Полный итог Actions, ZIP checksum и скриншоты следует брать с **точного SHA**
проверенного run. Linux source/QTest не заменяет Windows frozen доказательства.
Нет новых кубиков, cloud workers, Drive transport, CPU/RAM quotas, лицензирования
или автоматического повтора неопределённых внешних операций.
