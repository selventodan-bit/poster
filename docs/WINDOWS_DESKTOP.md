# Единое рабочее место Poster 2.0

Пользовательская сборка — переносимый `Poster.exe` с Python/Tk и зависимостями в `_internal`, без браузера. Никакие установщики и shell-команды при обычном запуске не вызываются. Первый сценарий — кнопка «Локальный тест»; обычная работа и очередь также доступны в том же окне. [Инструкция](windows_quickstart.md).

## Состав изменения

- `poster/recorder/app.py` остаётся тем же Recorder, с прежними подтверждениями, поколениями операций и состояниями. `desktop.py` добавляет Notebook, библиотеку проектов, очередь, результаты и систему.
- `workspace.py:EngineBridge` вызывает существующие `Engine`, `State`, `Registry` и `Runtime`; HTTP-протоколы и модели не заменяются. SQLite доступна только из потока asyncio. Остановка Engine ждёт начатые задания, а не отменяет HTTP-запросы.
- `workspace.py:local_test` владеет встроенным loopback-сервером на случайном порту и отдельными временными профилем, KB, проектом и очередью. Обычные RecognitionSession/Engine делают три публикации. В finally закрываются браузер, сервер и базы. Отмена при запуске Playwright больше не теряет дочерний процесс.
- `browser.py` проверяет Windows App Paths, стандартные каталоги и PATH, затем имеющийся Playwright cache. Выбранный браузер запускается с отдельным профилем Poster. Вызывающая сторона отдельно получает согласие на загрузку. В exe Playwright driver запускается напрямую, без повторного запуска exe с `-m`.
- Очистка рассматривает только `.poster/tmp/poster-*` с маркером владения, пропускает активные папки, ссылки и Windows junctions. Владение защищено OS-held FileLock: второй экземпляр Poster не удаляет активный тест первого. Отдельная блокировка сериализует очистку. Базы, проекты, ключи, браузеры и постоянные профили не очищаются.
- `desktop_entry.py` — windowed entry point; все постоянные пользовательские данные остаются в `.poster` рядом с exe. `build_windows_app.py` не включает браузер и private state, добавляет commit в BUILD_INFO.json и SHA256 рядом с ZIP.

## Воспроизводимые проверки

`tests/test_desktop.py` проверяет очередь/перезапуск без дублей, отказ непроверенному проекту, безопасную очистку и настоящий локальный тест кнопкой Tk с отменой и проверкой закрытого TCP-порта. Старые HTTP/KnowledgeBase/GUI регрессии сохраняются.

`check_windows_gui.py` запускает распакованный exe через Windows ShellExecute. Pywinauto вводит текст через системный clipboard и нажимает реальные OS mouse/keyboard. Подтверждения — настоящие MessageBox, без monkeypatch. Приложение по опциональному `POSTER_GUI_TEST_OUTPUT` только сообщает геометрию и безопасное состояние интерфейса; этот наблюдатель не принимает команд и не вызывает сервисы.

Сценарий проверяет:

1. Один запуск, один клик локального теста, три публикации и закрытый порт сервера.
2. Обычные кнопки распознавания, браузерной и независимой HTTP-публикации, сохранения, очереди, Engine и результатов на отдельном контролируемом сайте.
3. Новый запуск exe с прежними проектами и результатами; повторный запуск Engine без повторной публикации.
4. Установленный Chrome используется без загрузки; отказ в настоящем диалоге загрузки ничего не скачивает.
5. «Отменить тест» и закрытие окна останавливают локальный сервер; процесс выходит без аварии.

JSON локализаций читается явно как UTF-8; bootloader exe также включает UTF-8, независимо от системной ANSI-кодировки Windows. Регрессия отдельно воспроизводит cp1252. Закрытие браузера освобождает driver даже при исключении в context.close.

Windows matrix 3.11/3.12/3.13 сохраняет сервисные и Tk-регрессии; один и тот же portable exe собран на Python 3.12 и проверяется каждым runner. Native GUI отчёты/скриншоты отделены от профилей, cookies и ключей. Итог конкретного коммита публикуется в существующем PR №2 только после CI.

## Ограничения

Оригинальная CMS-матрица и ограничения прежнего [отчёта](USER_READINESS.md) сохраняются. GUI-автоматизация использует контролируемые сайты; это не утверждение о публикации на произвольном внешнем форуме. Сборка не подписана коммерческим сертификатом. Приложению нужна доступная для записи папка; полноценные Windows ACL и корпоративные политики установки браузеров зависят от системы пользователя.
