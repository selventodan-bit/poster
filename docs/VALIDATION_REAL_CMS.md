## Что реально переносится

Раньше HTTP-знания преимущественно определяли предпочтительный тип источника токена. Теперь `Rule.http_templates` содержит исполняемую структурную схему: порядок и типы операций, кодировки, форму вложенных объектов/массивов, роли контента и координаты зависимостей. Связи охватывают payload, URL path, query и разрешённые headers. Источники включают HTML hidden/meta, JSON, headers и безопасно разобранные JSON-конфигурации в inline script.

Шаблон **не содержит** URL, селекторов, имён полей, исходного текста, литеральных параметров, ID, cookies или токенов установки A. При применении структура сопоставляется с текущим локальным наблюдением B. Параметры и маршруты берутся с B; свежие значения должны присутствовать в локальных ответах и потребляющих запросах. Переупорядоченный или переименованный параметр связывается по уникальному свежему значению и доказанному источнику. Неоднозначность, несовместимая схема, поздний ответ и неизвестная зависимость отклоняют перенос.

Для обычной HTML-формы `preflight` проверяет локальный action/method и привязку к рецепту **без POST**. Это предварительная проверка, а не HTTP_VERIFIED. Произвольный SPA-протокол требует местного сетевого наблюдения. После разрешённой браузерной публикации создаётся HTTP_CANDIDATE; только отдельный успешный HTTP-тест допускает READY. Совместимый новый вариант сохраняется после этого теста. Импортированные правила не переносят доказательство локального успеха.

Протокольный тест дополнительно проверяет перенос двух операций с переименованным непрозрачным ID и зависимостями одновременно в payload и path. Это синтетический тест графа, а не доказательство такого многошагового протокола на перечисленных CMS. На оригинальных установках в данном наборе изучались одиночные запросы создания темы.

## Сравнение на второй настоящей установке

MyBB A обучается штатным способом, подтверждает HTTP и закрывает библиотеку. MyBB B использует новую установку, базу, origin, browser profile и авторизацию. Cookies, ID, токены и значения A не копируются.

В B установлен небольшой тестовый MyBB-плагин через стандартные hooks: прежний CSRF-токен публикуется в meta, а отправляемое имя меняется на `vouch`. Плагин передаёт полученное значение штатной проверке `my_post_key`; проверка токена, права и ограничения MyBB не отключаются. Это явно заданная конфигурационная вариация оригинального движка, а не неизменённая сторонняя тема или независимый внешний аудит.

Одна и та же запись B сравнивается с чистой библиотекой и с закрытой/повторно открытой библиотекой A:

| Условие | Построение HTTP-кандидата B | Отправки preflight | Независимый HTTP | Повторный проект |
|---|---|---|---|---|
| Чистая библиотека | LEARNING_REQUIRED, неизвестный динамический параметр | 0 | не отправляется | отсутствует |
| Знания A | HTTP_CANDIDATE, перенесена 1 операция и 2 свежие привязки | 0 | SUCCEEDED | SUCCEEDED |

Измеренное улучшение: **0/1 → 1/1 построенных кандидатов** на одной контролируемой паре с изменённым источником токена. Дообучение вручную не потребовалось. Выигрыш скорости поиска формы и поддержка других тем/версий не доказаны. На обычных A/Flarum/SMF чистая библиотека уже строила кандидата; дополнительный прирост успешности там не заявляется.

## Исправления, обнаруженные на настоящих установках

- Поле с именем `action` перекрывало DOM-свойство `form.action`; чтение action теперь использует HTML-атрибут и base URI.
- Кнопки preview/draft/upload конкурировали с публикацией. Их технические action/name исключаются; именованный submitter дополнительно ограничивает первую разрешённую отправку и блокирует фоновые черновики с тем же контентом.
- Поздно появляющиеся iframe и `about:srcdoc` требовали повторного снимка и проверки наследуемого origin. После навигации ожидается DOMContentLoaded.
- Hidden-поля с одинаковыми именами в поиске и композере требовали локального структурного селектора. Источники свежих параметров выбираются на странице текущего композера, а не на прежней странице входа.
- Пустые невыбранные file inputs больше не трактуются как загрузка файла. Различающиеся повторные поля и настоящие uploads остаются неподдержанными; одинаковые scalar multipart-дубликаты сворачиваются.
- MyBB возвращает 200/interstitial с последующим переходом. Workflow извлекает наблюдённую ссылку и читает тему. Flarum JSON:API возвращает ID; кандидат извлекает новый `data.id` и проверяет `/d/{id}`.
- Маршруты SMF с `;`, служебные topic-переходы и числовые query-ID теперь корректно сохраняются в безопасной постоянной ссылке. Секретные query-параметры удаляются.
- Установлен общий тайм-аут подтверждения 45 секунд с отдельным окном permalink 20 секунд, событием сетевого ответа и ограниченным read-only polling. Истечение времени означает UNKNOWN; повторного POST нет. Тест задержки 5,1 секунды подтверждает исправление прежнего лимита 4 секунды.
- CKEditor требует дождаться асинхронного `setData`; Summernote API должен обновлять исходный host, а не создавать редактор на editable div. Добавлен `html_lines`, сохраняющий экранирование и переводы строк в HTML.
- Непонятый финальный запрос без контента больше не исчезает из протокола как будто была только запись черновика. Перенос объясняет граф целиком либо отказывается.

## Как повторить

Заключительный локальный набор: **148 passed**, без пропусков, с настоящим Tk GUI через Xvfb; `ruff check .` и `ruff format --check .` прошли. Оба notebooks (Colab и Molab) выполнены локально: HTTP с новым CSRF, генератор и SQLite backup/restore прошли. Шесть первоначальных проверок переноса расширены тестами inline JSON nonce и блокировки фонового черновика.

В подготовленной среде:

```bash
cd /workspace/poster
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/python -m pytest -q
```

На Linux без дисплея GUI-тест требует Xvfb; CI запускает pytest через `xvfb-run`. Windows Recorder имеет отдельный CI job.

Для настоящих CMS нужны Docker, GitHub CLI с доступом к публичным upstream releases, Python `.[dev,recorder]` и Chromium. Каждый output должен быть новым:

```bash
.venv/bin/python scripts/run_cms_ci.py --engine mybb --output .poster/mybb-first-check
.venv/bin/python scripts/run_cms_ci.py --engine smf --output .poster/smf-first-check
.venv/bin/python scripts/run_cms_ci.py --engine flarum --output .poster/flarum-first-check
```

MyBB автоматически проверяет A и B; библиотека между ними закрывается и открывается заново. Серверы опубликованы только на loopback, контейнеры останавливаются в finally. Не запускайте эти три команды одновременно на одном порту; для параллельного запуска задайте разные `--port`. Штатные интервалы SMF соблюдаются ожиданием, а не отключением ограничения или повторным POST. PhpBB запускается отдельно по [инструкции стенда](real_engine_testing.md).

Оригинальные редакторы (Linux/Node.js):

```bash
npm ci --prefix scripts/integration/editors
.venv/bin/python scripts/check_original_editors.py
```

Синтетический benchmark остаётся отдельной командой `python -m poster benchmark-recognition --output NEW_DIRECTORY`. Его результаты нельзя складывать с таблицей настоящих CMS.

## Границы проверки и оставшиеся направления

- **wpForo:** официальный ZIP, WordPress plugin API, SVN/Trac и сайт wpforo.com недоступны из среды (proxy/connect 403). Сторонняя непроверенная сборка не использовалась; WordPress+wpForo browser→HTTP не подтверждён. Нужен доступ к официальному пакету. Подготовлены общий TinyMCE/SPA механизм, структурные compose-признаки и извлечение свежего nonce из inline JSON; это протокольные возможности, а не проверка оригинального wpForo.
- **Discourse:** попытка получить официальный `discourse/discourse_dev:release` завершилась `failed to register layer: no space left on device` при распаковке в среде с диском 32 GB. Установка и публикации не выполнены. Нужен runner с достаточным диском либо доступная разрешённая тестовая установка.
- **XenForo, vBulletin, Invision Community:** оригинальные лицензированные дистрибутивы и разрешённые установки не предоставлены. Сигнатуры и общие адаптеры не считаются поддержкой публикации; испытания не засчитаны. Для XenForo особенно требуется проверить оригинальные формы/редактор/AJAX на лицензированном экземпляре.
- Проверены конкретные конфигурации четырёх CMS. Другие версии, языковые пакеты, произвольные темы/плагины, дополнительные обязательные поля и внешние публичные форумы не подтверждены этим набором.
- Шаблоны консервативно сопоставляют типы и размер графа. Неизвестные изменения структуры требуют местного наблюдения и нового независимого теста. Закрытый Shadow DOM, cross-origin SSO/iframe, загрузки файлов и произвольные JS-вычисления остаются за пределами автоматического обучения. CAPTCHA, модерация и ограничения доступа не обходятся.
- Новый источник nonce разбирает только ограниченные JSON literals в HTML; функции, вычисления и неоднозначные источники не исполняются.
- Истечение серверной сессии требует повторного входа/обучения. Перезапуск Recorder проверяется закрытием браузера и новым загрузчиком HTTP-проекта; перенос сессии между установками не выполняется.
- Live Google Drive и размещённые Colab/Molab не запускались; прежние контролируемые тесты Drive и локальное исполнение обоих notebooks сохранены.

Workflow GitHub Actions включает Python 3.11/3.13, Windows Recorder, оригинальный phpBB, matrix MyBB/SMF/Flarum и оригинальные редакторы. Только безопасные JSON-отчёты публикуются как artifacts. Фактический статус конкретного HEAD следует смотреть в PR №2; добавление job само по себе не означает успешное выполнение.
