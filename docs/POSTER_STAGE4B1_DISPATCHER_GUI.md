# Poster 3.0 — 4B.1: Windows Dispatcher

## Первый запуск

Скачайте artifact **poster-maker-windows** из успешного workflow `tests` нужного
коммита. Внутри artifact находится `poster-maker-windows.zip`, его SHA256 и
`build-report.json`. Проверяется именно внутренний ZIP. Полностью распакуйте его
в отдельную папку. Не переносите EXE отдельно от `_internal` и `BUILD_INFO.json`.

- `Poster.exe` открывает прежний Full Maker. Его кнопка **Dispatcher** открывает
  самостоятельное окно управления очередью.
- `PosterDispatcher.exe` открывает это окно напрямую двойным щелчком.
- `PosterService.exe` и `PosterWorker.exe` — внутренние процессы. Вручную их
  запускать не нужно. Worker без параметров/канала разрешения граф не исполняет.

Устанавливать Python, Git или Docker и открывать PowerShell не требуется.
Первый запуск не скачивает зависимости или браузер. Для Browser-кубиков worker
использует существующий ChromiumProvider и установленный Chrome/Chromium/Edge,
не встроенный Qt-браузер Maker. HTTP/данные/файлы обходятся без браузера.
Windows 10/11 x64; подпись EXE и автоматическое обновление в этот этап не входят.

Lite `poster-windows.zip` сохраняет прежний Tk Maker/Recorder и исполнение графов.
В нём есть headless launchers с общим runtime, но нет Qt Dispatcher GUI.
Для нового окна Dispatcher скачивайте Full.

## Добавление и запуск

1. Сохраните проект в Maker, затем в Dispatcher выберите **Добавить проект…**.
   Используется нативный диалог выбора `.postergraph.json`.
2. В **Проектах** видны название, ID, версия снимка, последний статус, запуски,
   ошибки/неопределённые результаты, активные процессы и длительность. Двойной
   щелчок открывает сведения. Поиск, сортировка и контекстное меню работают с
   настоящими зарегистрированными проектами.
3. Выделите один или несколько проектов и нажмите **В очередь**. Для каждого
   проекта задайте входы и индивидуальный timeout. Флажок «Передать» отличает
   отсутствующий вход от пустой строки. Есть текст, число, boolean и JSON.
   Защищённые входы вводятся в password-поле. JSON сохраняет исходные типы.
4. Пока обслуживание остановлено, задайте количество workers и лимит на один
   проект, нажмите **Применить**. Это независимые процессы, не потоки GUI.
   Новые лимиты применяются при следующем запуске обслуживания; живой Scheduler
   не перенастраивается. Timeout в настройках — начальное значение для новых
   заданий; принятые задания сохраняют свой timeout.
5. **Запустить обслуживание** запускает Dispatcher 4A. В **Заданиях и истории**
   видны реальные состояния SQLite, worker PID, время, попытка и диагностический
   код. Страницы ограничены 200 строками. Поиск/статус/сортировка выполняются
   службой; загрузка и RPC не блокируют Qt-поток. Выделение сохраняется.
6. **История / результат** показывает события и безопасный отчёт только после
   проверки SHA256. **Открыть рабочую папку** открывает файлы, созданные графом.
   Содержимое входов, cookies и секретов в отчёт не выводится.

При изменении исходника добавьте его ещё раз: обновится регистрация для будущих
заданий. Уже принятые задания и регистрация используют зафиксированный snapshot,
не читают изменяемый исходник при запуске. Исходник после импорта может быть
перемещён. **Убрать из списка** удаляет регистрацию, сохраняя историю, snapshots
и пользовательские файлы.

## Жизненный цикл и аварии

GUI — клиент самостоятельной службы пользователя, а не владелец Scheduler.
Закрытие окна, включая аварийное завершение GUI, оставляет задания работать.
Откройте окно снова для подключения к той же службе. Повторное окно не создаёт
второй Scheduler. Это фоновый процесс текущего пользователя, не зарегистрированная
служба Windows SCM и не автозапуск при входе в систему.

- **Остановить приём** запрещает новые leases и ждёт завершения уже принятых
  заданий. Ожидающие остаются в очереди.
- **Отменить выбранные** немедленно отменяет PENDING либо передаёт запрос остановки
  активному worker. Принятый сайтом POST не откатывается. При неопределённости
  итог будет UNKNOWN, даже если остановка запрошена пользователем.
- **Завершить службу** останавливает приём, дожидается активных заданий и завершает
  процесс Service. Для запуска снова нажмите **Переподключиться**.
- **Проверить после сбоя** вызывает существующий `reconcile` под lock Dispatcher.
  UNKNOWN становится REVIEW_REQUIRED. Сам граф при этом не исполняется.

При UNKNOWN/REVIEW_REQUIRED проверьте внешний сайт вручную. Автоматического retry
и возврата неопределённой записи в PENDING нет. Неожиданное исключение до внешних
действий допускает FAILED; после durable `effects_possible` сохраняется UNKNOWN.
Это относится также к формированию результатов и очистке, не только к ошибкам
кубиков. Диагностика использует фиксированные коды и номера строк без исходного
текста исключения.

Scheduler владеет анонимным каналом worker и Windows Job Object с kill-on-close.
До открытия канала PID и process birth фиксируются в SQLite. Авария Service
закрывает его Job Objects, worker также контролирует EOF. При восстановлении
проверяется birth PID; чужой процесс с повторно использованным PID не завершается.
На POSIX остаются существующие process groups. Обрыв клиента на аутентификации
не должен завершать RPC-loop службы.

В Linux Chromium может создать отдельную session/process group. Поэтому
`killpg(worker)` дополнен меткой run, наследуемой только его дочерними процессами:
при завершении/восстановлении удаляются оставшиеся процессы этой метки текущего
UID с проверкой birth. Значения окружения не журналируются. Регрессия намеренно
приостанавливает Playwright driver перед аварией worker, исключая зависимость
от его обычной EOF-очистки; параллельное другое задание должно продолжить работу.

## Ключи, профили и постоянная папка

Новая очередь живёт в `%LOCALAPPDATA%\Poster\Dispatcher`, не в каталоге EXE.
В Linux source-режиме — `$XDG_STATE_HOME/Poster/Dispatcher` или
`~/.local/state/Poster/Dispatcher`. Для изолированных испытаний есть
`POSTER_DISPATCHER_WORKSPACE`. Это host-настройка, граф её не задаёт.

В папке находятся отдельная `dispatcher.sqlite`, её `.data`, `queue.key`,
зашифрованный `catalog.enc`, IPC auth key и безопасные настройки. Сохраните
резервную копию всей папки после остановки службы. Потерянный `queue.key` для
существующей очереди не создаётся заново. Старая `.poster` Maker/Engine не
мигрируется, не удаляется и не подменяется этой папкой.

При импорте проверяется расшифровка защищённых токенов проекта. Для обычного
расположения Maker используется существующий `.poster/private/session.key`.
Для экспорта в другую папку GUI предлагает выбрать именно существующий ключ
Maker. Неверный ключ даёт понятную ошибку; регистрация не добавляется.

Ключ проекта хранится внутри зашифрованного каталога/задания под ключом очереди.
Worker получает ключ очереди через анонимный stdin-канал, затем добавляет ключ
проекта к существующему механизму `auth._legacy_keys` только в своём процессе.
Оригинальный SecretRef/sidecar и типы значений не переписываются. Ключи не входят
в argv, публичный JSON, observer или журнал. Сервис не меняет глобальный ключ
Maker при переключении между проектами.

Для браузерного задания можно явно выбрать сохранённый `profile_….enc` и его
`session.key`. Снимок профиля шифруется в задании. Существующий execution lock
исходного профиля сериализует конкурирующие запуски; PROFILE_BUSY виден в истории.
Без выбора профиля создаётся изолированный контекст. Изменения cookies worker
не сохраняет обратно в профиль Maker автоматически.

На Windows приватные каталоги/файлы защищаются owner-only protected DACL через
WinAPI; внешняя console-утилита `icacls` не запускается. На POSIX сохраняются
права 0700/0600. Это приложение текущего пользователя, не многопользовательский
remote API. Защита графов не является OS-песочницей для произвольного Python:
исполняются только зарегистрированные типы действий, JSON не исполняется как код.

## Входные файлы и результаты

Рабочая папка **каждого** задания изначально пуста. Snapshot включает графы и
зашифрованные sidecars, но не произвольные соседние CSV/XLSX/медиа. GUI объясняет
это в сведениях о проекте и при файловых ошибках.

Граф может создать входные файлы действиями Files/CSV/Excel из переданных данных
либо загрузить их через HTTP. Относительные пути находятся внутри workdir.
Абсолютный путь к файлу в Maker не получает автоматического доступа из worker.
Выход через `..`, symlink/junction и абсолютный путь вне workdir запрещён
существующим FileSandbox. Безопасный импорт пользовательских ресурсов отложен;
не следует подменять его отключением sandbox или общей папкой всех запусков.

Публичный отчёт содержит метаданные, безопасные ошибки и пути результатов.
Полные результаты зашифрованы в `results.enc`; GUI их не расшифровывает для
показа секретов. Намеренно созданные графом output-файлы остаются в приватной
рабочей папке и могут содержать данные, которые пользователь поручил записать.
Автоматической очистки истории/snapshots/output нет. Временные расшифрованные
копии графов удаляются worker; чужие каталоги не очищаются.

## Упаковка и проверка

`scripts/windows_dispatcher.spec` делает две независимые PyInstaller Analysis:
GUI и headless. У headless исключены PySide6/Tkinter и их runtime hooks.
Один COLLECT помещает DLL Python, Qt, Playwright driver и остальные зависимости
в общий `_internal`. EXE/PYZ отдельных ролей занимают дополнительное место, но
Runtime Python (DLL версии и ABI-stub), Qt WebEngine и node driver не копируются в отдельные runtime-папки.
Изоляция сохраняется на уровне OS-процессов.

`BUILD_INFO.json` содержит SHA сборки, роли и SHA256 EXE. В каждом executable
скомпилирован build marker. Несовпадение версии manifest, отсутствие или
повреждение launcher запрещает запуск; поиска `python.exe`/pip или fallback
на системный интерпретатор нет. Перенос/обновление папки программы выполняйте
после явного завершения службы. Установленная версия работающей службы должна
совпадать с GUI.

`build-report.json` и Actions notice содержат фактические размеры сжатого ZIP,
распакованного приложения, каждого EXE и список Python DLL. Они относятся к
конкретному коммиту, а не к приблизительной оценке размера.

Обязательная CI-матрица прежних этапов сохранена. Добавлены:

- Регрессии unexpected worker exception до графа, после принятого POST и при
  сериализации результатов, включая отсутствие retry после reconcile/run.
- Service lifetime, разрыв на аутентификации, immutable registrations, разные
  ключи Maker/очереди, проверка SHA отчёта, 430 заданий и страницы по 200,
  реальные settings и fail-closed integrity launcher на Linux и Windows.
- Нативный Qt-сценарий с настоящим event loop, двумя worker и повторным
  подключением на Ubuntu/Windows.
- `scripts/check_dispatcher_windows_gui.py`: готовый ZIP, ShellExecute,
  нативные файловые диалоги, pywinauto mouse/keyboard, реальные PID/executable
  paths, управляемый HTTP overlap при 2 workers и отсутствие overlap при 1,
  output-файлы, история, cancel/timeout, аварии GUI/worker/Service, отсутствие
  повторного POST, сохранение защищённой переменной **через Maker GUI** и
  исполнение frozen worker, Chrome и cleanup, перенос приложения.

Harness в Windows CI имеет Python. Это явно записывается в отчёт: проверка
доказывает отсутствие зависимости приложения от этого Python через ограниченный
PATH, очищенные переменные и проверку реальных executable путей каждого worker;
физически чистая ОС без установленного Python этим не подменяется.
Наблюдение read-only: observer сообщает координаты/статусы, а не команды;
содержимое входов не включается. Artifact **dispatcher-windows-gui** содержит
безопасный `report.json` и настоящие скриншоты Windows, без приватной базы,
каталога, ключей и observer.

Локальный source-запуск для разработчика:

```bash
uv sync --frozen --extra dev --extra maker
uv run python -m poster.dispatcher.qt_app
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
```

## Совместимость и границы этапа

Сохранены Store schema 4A, immutable snapshots, GraphRunner, графы v1/v2,
78 действий, SecretRef, профили, подпроекты и общий budget. Старые HTTP Engine,
Recorder, SQLite/Drive/KnowledgeBase и READY/Workflow v1 не заменены новой очередью.
Service, JSON RPC и Launcher не импортируют Qt. На Linux те же графы продолжают
исполняться исходным CLI/GraphRunner/Dispatcher без Windows GUI.

Не реализованы distributed/VPS/Colab/Molab Dispatcher, удалённая авторизация,
SCM/autostart, расписания, лицензирование, retry неопределённых записей,
универсальный перенос файловых ресурсов, CPU/RAM quotas, browser-кубики внутри
подпроектов и полная совместимость с ZennoPoster. UI использует постраничный
список заданий; удалённой загрузки результатов и их облачной синхронизации нет.
Следующий этап должен отдельно проектировать безопасные resource bundles и
удалённые transport/identity/lease contracts, сохраняя headless исполнение.
