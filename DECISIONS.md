# Решения MVP

1. Одна Python-библиотека и CLI, stdlib fixture-сервер; без Redis, контейнеров и платных API. Вертикальный срез проверяется настоящим Chromium и TCP HTTP.
2. Recorder: отдельный persistent profile, Playwright и Tk UI. Сырые запросы, ответы, действия и DOM только в памяти; HAR не экспортируется. Два захвата сравниваются в одной UI-сессии. «Открыть» позволяет переобучить старый проект с сохранением настроек; экспорт новой версии отдельно, история в SQLite.
3. Автосборка ограничена одной URL-encoded POST/PUT/PATCH с двумя маркерами. Hidden-поля извлекаются CSS из свежего GET; неизвестное происхождение/JS-трансформация → REVIEW. Многошаговые API пока задаются вручную.
4. READY — JSON schema_version=1 с SHA-256 каждого файла. Это строже пустого маркера: предотвращает смешанные версии. Пишите последним. Это контроль полноты, а не цифровая подпись/доверие к автору.
5. Registry хранит неизменные снимки; плохое обновление сохраняет рабочее. Очередь фиксирует проект и текст при постановке; уже поставленные задачи не меняются. Удаление/отключение останавливает ещё не начатые задания.
6. Точные allowed_hosts, проверка каждого редиректа, запрет HTTPS downgrade. CookieJar соблюдает domain/path/secure; auth-заголовки только исходному origin. 307/308 после записи автоматически не повторяются. Порт не является отдельной политикой. Это проверка адресата, не полный DNS/SSRF sandbox.
7. Только GET/HEAD имеют bounded retry. Ошибка после потенциальной записи → UNKNOWN; read-only recovery может подтвердить результат, но не делает POST. Отсутствие подтверждения не доказывает отсутствие записи.
8. SQLite WAL + транзакции + OS-lock: один Engine на локальную БД. Lock не координирует разные машины/копии БД. Перед переносом остановите старый Engine. Снимок для восстановления выбирает оператор, а не ненадёжная эвристика «последний файл».
9. План конечный: targets.csv или enqueue. Уникальность проект/target-id/кампания/seed без ревизии защищает от дублей сканирования. Обновление шаблона не запускает повторную публикацию.
10. Генератор data-only, без eval/Jinja/AI. Локали и product_id сохраняют связь описаний. Готовый текст и provenance хранятся в БД. Без READY — локальный dev-режим, с READY — согласованный снимок и предыдущая рабочая версия при ошибке.
11. Drive v3 REST + google-auth: OAuth authorized-user/service account/ADC. Сканируется только выбранное дерево, ревизии кешируются в процессе, pagination/backoff ограничены. READY обязателен каждому проекту и всему content. Аккаунт/ключи предоставляет оператор вне репозитория.
12. Hosted Molab/Colab, реальный Drive и Windows GUI требуют отдельных проверок. Бинарные uploads, браузерный fallback, автоматический ремонт схем и распределённые воркеры — последующие версии.
