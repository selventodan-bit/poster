# ТЕХНИЧЕСКОЕ ЗАДАНИЕ — Python Recorder + HTTP Automation Engine

**Редакция:** MVP 0.1 / 22 октября 2026 года
**Адресат:** Codex, инженер-разработчик
**Статус:** начать реализацию; не превращать работу в очередное обсуждение архитектуры.

> **Главный принцип заказчика:** «Сначала получаем работающий, пусть сырой продукт. Потом тестируем, исправляем и расширяем». Не писать многонедельный дизайн-док вместо рабочего кода.

## 0. Задача одним абзацем

Создать переносимую систему веб-автоматизации на Python, напоминающую ZennoPoster по сценарию работы, **но выполняющую повторяющиеся операции преимущественно лёгкими HTTP-запросами без постоянного браузера**. На Windows отдельный **Recorder** записывает действия пользователя на сайте и автоматически производит многоразовый проект HTTP-сценария. Проекты, сохранённые в **Google Drive**, работающий **Engine** подхватывает **без перезапуска**; Engine выполняет подготовленные действия, обрабатывает разные сайты конкурентно, сохраняет результат, возобновляет работу после перезапуска и получает заголовки/тексты от **независимого шаблонного генератора контента** (словари, фразы, товары/темы, города, шаблоны). Должно запускаться локально, на VPS, в Colab и Molab в рамках ограничений этих сред. Никакой обязательной генерации сценариев внешней ИИ-моделью.

## 1. Контекст заказчика и принятые решения

1. Раньше заказчик пользовался XRumer и ZennoPoster и арендовал дорогостоящие VPS/серверы. Теперь цель — экспериментировать с собственными сценариями с максимально низкой стоимостью инфраструктуры, без крупных ежемесячных обязательств.
2. Автоматизация не должна быть привязана исключительно к форумам. Возможны разные форумы, CMS, блоги и формы на сайтах, для которых оператор уже имеет подходящую сессию/учётную запись.
3. **Оператор сам выбирает сайты.** Не строить модуль чтения правил сайтов или автоматического определения «разрешения на постинг». Это вне задачи движка. Нужны технические ограничения безопасности, например запрет отправки cookies одного сайта постороннему хосту.
4. В идеале новый сайт добавляется так: пользователь обучает Recorder, получает папку проекта, переносит её на Google Drive; запущенный Engine находит папку, проверяет проект и включает в очередь **без перезапуска**.
5. Нужна возможность пополнять словари и шаблоны контента таким же образом — без перекомпиляции и перезапуска.
6. **Не использовать тяжёлый Chromium для каждой задачи.** Recorder использует браузер локально на Windows. Исполнитель в первую очередь использует `httpx`/`asyncio`. Поддержка браузерного исполнения — запасной режим для сложных сайтов, последующая версия.
7. Архитектура переносимая. Molab/Colab — возможные вычислительные среды, **не обязательная инфраструктура**, и не предполагается, что эти сервисы гарантируют вечную фоновую работу.
8. Отдельные компоненты: Recorder → Project Builder → Drive Sync → Engine; генератор контента → очередь → Engine.
9. Сначала минимальный рабочий вертикальный срез с реальным тестированием. Далее итерации по фактическим результатам.

## 2. Требования к MVP: что ОБЯЗАТЕЛЬНО должно работать

### 2.1 Recorder, локально на Windows

- Запустить выделенный профиль Chromium через Playwright (профиль не должен совпадать с основным пользовательским профилем).
- Начать/остановить запись одной реальной пользовательской операции: переход к нужной форме, заполнение, отправка, подтверждение успеха.
- Собрать относящиеся к операции HTTP-запросы/ответы (метод, URL, тип данных, query, тело, статус, редиректы; только нужные заголовки), структуру HTML-формы, имена полей, DOM-селекторы, возможные CSRF-поля и состояние сессии.
- Для определения полей заголовка/тела предлагать тестовые **уникальные маркеры** (`REC_TITLE_<id>`, `REC_BODY_<id>`); находить их в отправленных запросах и превращать в переменные `{{title}}`, `{{body}}`.
- Автоматически находить вероятную операцию отправки (POST/PUT/PATCH или API-запрос) и необходимые предшествующие GET/прочие запросы.
- Анализировать **возможные** динамические параметры: hidden fields, CSRF-токены, временные идентификаторы. Если происхождение токена не установлено, **не притворяться**, что сценарий надёжен; показать статус `REVIEW`.
- Допускать вторую запись того же действия с другими маркерами. Сравнение записей помогает отделять постоянные и динамические значения, но не считать любую изменяющуюся строку токеном автоматически.
- Экспортировать готовую папку проекта в установленном формате и явно показывать статус `HTTP_READY`, `REVIEW`, `BROWSER_REQUIRED`.
- Минимальный интерфейс: «Новый проект», «Запись», «Стоп», «Анализ», «Проверить», «Экспорт». Подойдёт простое локальное окно `tkinter` или локальный интерфейс; не тратить недели на дизайн UI.
- Не рассчитывать, что один HAR всегда достаточен: дополнительно фиксировать последовательность действий и снимок формы/DOM. Сырые диагностические записи не отправлять никуда автоматически.

### 2.2 Создатель проектов (Project Builder)

- Из записи создать **декларативный проект**, а не хардкодить URL, поля, ключи и контент в исходниках Engine.
- Формат проекта версионировать (`schema_version: 1`), валидировать перед включением.
- Конфигурация проекта определяет: идентификатор сайта, базовый URL, допустимые домены, режим (`http`/`browser`), целевые страницы, сценарий, файл защищённой сессии, поля для контента, признаки проверки результата и параметры обработки.
- Разрешить ручные правки YAML после автогенерации (но ручное создание сценария **не должно быть обязательным** для простых форм).
- Возможность повторного обучения: новый Recorder-захват для старого проекта, сравнение шагов, обновление шаблона с сохранением настроек/истории.
- Никакого исполнения произвольного удалённого Python-кода, лежащего в папке Google Drive. Новые проекты — **данные и ограниченные декларативные команды**. Сложные плагины-код отдельно устанавливаются оператором в Engine.

### 2.3 HTTP Engine

- Python 3.11+; асинхронные операции на базе `asyncio` + `httpx`.
- Универсальные операции: `REQUEST` (GET/POST и др.), `EXTRACT` (CSS/HTML, JSONPath или простая JSON-path выборка, regex только для специально заданных случаев), `SET`, `ASSERT`, `VERIFY`, `WAIT`.
- Сессионные cookies/заголовки; корректные редиректы, content-type, формы с URL encoding, multipart при необходимости. Выделять динамический CSRF из актуальной страницы перед отправкой.
- Строгая подстановка переменных из ограниченного контекста выполнения: `title`, `body`, `target_url`, `csrf`, пользовательские поля. Отсутствующая переменная = понятная ошибка, а не пустая строка.
- Проверять хост запроса против `allowed_hosts` проекта, чтобы секреты не ушли на чужой домен из неверной или подменённой конфигурации.
- Асинхронная очередь; начальная настраиваемая параллельность `max_concurrent_http=10`, `max_per_host=1` (не фиксировать жёстко). Лимиты таймаутов, повторов и задержек также задаются конфигурацией.
- Проверка **фактического результата** операции: код HTTP 200 сам по себе не означает публикацию; требуется распознать ссылку, ID, подтверждающий элемент или целевое состояние страницы.
- Различать результаты `SUCCEEDED`, `FAILED`, `AUTH_EXPIRED`, `REVIEW_REQUIRED`, `UNKNOWN`. При `UNKNOWN` (например, таймаут после отправки) сначала проверять, что произошло, **не отправлять бездумно повторно**.
- Логи: сайт, проект, время, операция, результат, URL результата, диагностика без секретов.
- Режим `dry-run` для проверки преобразования и заполнения переменных без реальной отправки.

### 2.4 Google Drive: горячее подключение проектов

- Официальный Google Drive API; пользовательская авторизация с OAuth или разрешённый ему service account. **Не хранить токены OAuth и ключи шифрования внутри общего открытого проекта.**
- Каждые настраиваемые 60–120 секунд (по умолчанию 60) проверять изменения в каталоге `projects/` и `content/` через Drive API; поддерживать постраничную выдачу и backoff при квотах/временных ошибках.
- Скачивать изменения в локальный кеш и проверять валидность; **атомарно переключать версию**, только когда файлы полностью получены. Манифест/маркер `READY` загружается последним, чтобы не подхватить недозагруженную папку.
- Новую папку → зарегистрировать проект и ставить задания; изменённую → заменить конфигурацию **для следующих** заданий; удалённую/отключённую → больше не назначать новых задач; текущие не обрывать без специальной команды.
- Должен быть также `local_folder`-провайдер, использующий **тот же формат проекта** — обязательный для разработки и тестирования без доступа к Google Drive. Это не альтернативная архитектура, а сменный storage adapter.
- Не сканировать всю Drive каждые несколько секунд: кешировать идентификаторы и ревизии.

### 2.5 Генератор контента из словарей (без обязательного ИИ)

- Отдельный модуль `content_generator`, **не знает**, что такое HTTP, cookies, форум или форма.
- Отдельные файлы для названий продуктов/тем, ключевых фраз и модификаторов, городов, вступлений, готовых предложений, привязанных описаний, шаблонов публикаций, кампаний, ссылок/целевых значений (если нужны).
- Локали (`it`, `fr`, затем расширяемые), корректная привязка словарей к языку, продукту и шаблону. Нельзя произвольно смешивать несовместимые описания разных продуктов или языков.
- В шаблонах поддержать простые макросы: `{{product.name}}`, `{{description}}`, `{{intro}}`, `{{keywords}}`, `{{cities}}`; выбор N элементов без повторов; необязательные блоки; несколько структур шаблонов.
- Генерация возвращает нормализованный объект `{title, body, metadata}` независимо от платформы публикации.
- Идентификатор шаблона, значения словарей и random seed фиксируются в журнале — можно восстановить ровно тот же вариант.
- Поддерживать горячее обновление словарей после изменения файлов на Google Drive.
- **Не требовать ИИ/LLM или API-ключей для работы модуля.** LLM позже может быть отдельным необязательным плагином.
- Демонстрация на **информационной фармацевтической теме**: `products.csv` (названия препаратов), `descriptions.csv` (проверенные, привязанные к конкретному препарату описания), `cities_it.txt`, `cities_fr.txt`, `keywords_it.txt`, `intros_it.txt`, `templates/italian_info.txt`. Пример демонстрирует архитектуру, а не обещания продажи рецептурных препаратов или достоверность рекламных заявлений.

### 2.6 Хранение состояния и восстановление

- Локальный SQLite с таблицами `projects`, `jobs`, `executions`, `content_variants`, `replay_artifacts` и отдельной таблицей версии схемы.
- Состояния задач: `PENDING` → `LEASED` → `RUNNING` → `SUCCEEDED` / `FAILED` / `UNKNOWN` / `REVIEW_REQUIRED`.
- Сохранение результата после каждого значимого перехода; `run_id`, `job_id`, `content_id`, `project_id`, `project_revision`, `attempt`, время, `result_url`.
- Для облаков с временным диском — выгрузка **резервных снимков SQLite/журнала на Drive** и восстановление при старте. Использовать согласованные snapshot'ы базы, не копировать «на горячую» один файл SQLite в небезопасном состоянии.
- В MVP один активный Engine на одно хранилище состояния; два одновременно запущенных в разных облаках без общей транзакционной базы не должны независимо исполнять одни и те же задания.
- При рестарте Engine восстанавливает проекты, прогресс, очередь, историю результатов. Не создавать дубликаты из-за повторного сканирования Drive.

## 5. Пример декларативного проекта (нормативный интерфейс, детали можно уточнить в ходе кода)

`site.yaml`:

```yaml
schema_version: 1
id: example-forum
base_url: https://forum.example.org
allowed_hosts:
  - forum.example.org
mode: http
enabled: true
workflow: workflow.yaml
verification: verification.yaml
auth_file: session.enc
campaign: italian_info
schedule:
  max_concurrent: 1
  min_interval_seconds: 120
```

`workflow.yaml` (упрощённая тестовая HTML-форма; **не** конфигурация какого-либо реального форума):

```yaml
schema_version: 1
steps:
  - id: open_target
    op: request
    method: GET
    url: "{{target_url}}"
    save_as: page

  - id: extract_csrf
    op: extract
    source: page
    kind: css_attribute
    selector: 'input[name="csrf_token"]'
    attribute: value
    save_as: csrf

  - id: submit
    op: request
    method: POST
    url: "{{submit_url}}"
    form:
      subject: "{{title}}"
      message: "{{body}}"
      csrf_token: "{{csrf}}"
    save_as: submit_response

  - id: check
    op: verify
    kind: response_or_followup
    source: submit_response
    rule: publication_confirmation
```

Это пример **формата DSL**, а не обещание поддержки именно этих операций из коробки до их реализации. В первую очередь обеспечить перечисленные минимальные операции и проверить fixture-тестами.

## 7. Процесс работы глазами пользователя

### A. Создание нового проекта

1. Windows → `Recorder` → «Новый проект».
2. Ввод домена, запуск браузера, авторизация оператором.
3. Кнопка «Записать», ручная операция с уникальными маркерами в полях.
4. «Стоп» → анализ HTTP + DOM; при необходимости вторая пробная запись.
5. «Проверить HTTP replay» на контролируемом тестовом действии. Если требуется проверка в реальном сайте, оператор явно запускает тест и понимает, что действие может быть выполнено.
6. Статус `HTTP_READY` или диагностическое `REVIEW`/`BROWSER_REQUIRED`.
7. «Экспорт» → папка проекта; добавление в Drive, последним загружается `READY`.
8. Уже работающий Engine через ≤120 сек обнаруживает проект, проверяет и ставит разрешённые задания в очередь. Ручного перезапуска нет.

### B. Обновление действующего проекта

1. Оператор меняет YAML или переобучает Recorder.
2. Загружает новую версию проекта.
3. Engine подхватывает ревизию; новая версия используется для следующих задач, текущие не мутируют на ходу.
4. При ошибке проекта старую исправную ревизию не уничтожать до подтверждения новой.

### C. Пополнение контента

1. Добавил строки `products.csv` или `cities_it.txt`, новый файл фраз/шаблон.
2. После обновления кэша новые данные используются **в новых генерациях**, старые задания не меняются.
3. Система не начинает бесконтрольно создавать задания по каждой комбинации автоматически: политика генерации и число заданий задаются кампанией.

### D. Перезапуск Molab / Colab / VPS

1. Движок загружает секреты из безопасного локального источника/переменных окружения.
2. Синхронизирует Drive, восстанавливает последнюю согласованную резервную копию состояния.
3. Проверяет незавершённые и `UNKNOWN`-операции, продолжает только те, для которых подтверждено отсутствие повтора.
4. **Нельзя обещать бесконечную фоновую работу в Molab/Colab или автоматический restart без разрешённого планировщика.**

## 8. Статусы и диагностика

Проект: `NEW`, `ANALYZING`, `HTTP_READY`, `REVIEW`, `BROWSER_REQUIRED`, `DISABLED`.

Задача: `PENDING`, `LEASED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `AUTH_EXPIRED`, `UNKNOWN`, `REVIEW_REQUIRED`.

Отчёт минимум: временная метка, проект, ревизия, target, кампания, выбранный шаблон, контент-ID, статус, URL результата, безопасная причина ошибки. Не записывать cookies, bearer-токены, пароли, полные сырые HAR в общие логи.

## 9. Важные границы первой версии

**В MVP обязательно:** Windows Recorder, хотя бы две локальные тестовые веб-формы, успешная автоматическая сборка проекта для простой HTML-формы, HTTP replay без браузера, валидатор, hot reload local folder и Drive, генератор из словарей, SQLite, восстановление, README и запускаемый demo.

**Не включать в MVP без нужды:** красивую ERP-панель, масштабирование на сотни распределённых процессов, бесконечный каталог готовых CMS, произвольный JS в облаке, автогенерацию через платные LLM, десятки вариантов прокси, обход CAPTCHA/anti-bot, модули обхода ограничений площадок, сложные адаптеры социальных сетей. Поддержка Playwright в облачном Engine — опциональная следующая итерация, не условие готовности MVP.

**Производительность:** начинать с примерно 10 одновременных HTTP-задач глобально и 1 на домен, конфигурируемо. Число 100 сайтов — целевая возможность каталога и очереди, не требование открыть 100 браузеров одновременно.

## 10. Технические риски и их правильная обработка

1. **Непереносимая авторизация:** cookie может истечь, зависеть от дополнительного состояния или потерять силу. Вывести `AUTH_EXPIRED`, остановить соответствующие задачи, предложить новый Recorder-захват. Не считать cookies вечными.
2. **JS-зависимый workflow:** HTTP replay не всегда возможен. Честный статус `BROWSER_REQUIRED`; не выдавать сетевой захват за готовый проект.
3. **CSRF/одноразовые значения:** извлекать из свежего ответа, не зашивать старое значение из записи.
4. **Дубликаты после сетевого таймаута:** статус `UNKNOWN` + verify-before-retry. Idempotency гарантируется только там, где сайт предоставляет идентификаторы/подтверждение, иначе осторожный ручной разбор.
5. **Google Drive как очередь:** Drive — библиотека/конфигурации/backup, но не высокочастотная транзакционная очередь; SQLite — для локального исполнения, общий DB — в будущем для множества воркеров.
6. **Безопасность:** шифровать `session.enc`; ключ за пределами Google Drive; допустимые хосты; исключать секреты из диагностик; отказ от автоматического исполнения кода из Drive.
7. **Облачные ноутбуки:** runtime может остановиться, диск быть временным, политика запрещать постоянные фоновые задачи. Не создавать архитектуру, зависящую от вечного Molab.
8. **Данные и языки:** избегать необоснованных медицинских утверждений и случайного смешения продукта с чужим описанием. Не копировать рекламные заявления из чужих постов как достоверные факты.
9. **Изменения веб-форм:** Recorder должен уметь открыть старый проект для переобучения конкретного шага.

## 11. Что известно о протестированной вычислительной среде (справка, НЕ гарантии)

На Molab пользователь лично проверил:

- `gVisor Linux 4.19`, root в контейнере;
- `GenuineIntel`, family 6, model 207 (`0xCF`), commercial model скрыта; виртуальная среда сообщает 20 логических CPU;
- в кратком CPU-тесте масштабирование до ~19,33 эффективных CPU;
- выделение и RSS около **144 GiB** в тесте памяти; не гарантирует постоянное выделение ресурса;
- HTTPS Google/GitHub/PyPI/Hugging Face/example.com ответил `HTTP 200`, DNS тоже работает;
- процесс продолжал логировать примерно **три часа** после закрытия браузера и выключения локального ПК;
- это не доказательство возможности официально держать постоянно работающий сервер; Molab имеет ограничения на постоянные фоновые вычисления и на длительность сессий.

Вывод: переносимость обязательна. Нельзя пытаться решить надёжность Engine увеличением количества ядер.

## 12. Порядок разработки: первые реальные результаты вместо ещё одного плана

### Итерация 1 — рабочий локальный вертикальный срез (первый приоритет)

- Создать репозиторий, зависимости, точные команды запуска, две локальные fixture-площадки (обычная HTML-форма и форма с меняющимся CSRF).
- Реализовать минимальный Recorder, автоматически определяющий submit-запрос и поля с маркерами.
- Экспортировать `site.yaml` + `workflow.yaml` и выполнить тот же сценарий в `httpx` **без Chromium в процессе Engine**.
- Проверить, что обе тестовые площадки возвращают реальный подтверждённый результат.
- Принести работающий код, тесты, команды запуска и список фактических ограничений. **Не останавливаться на диаграмме и макете.**

### Итерация 2 — подключение новых сайтов без перезапуска

- Сначала `local_folder` watcher/poller → новый проект без рестарта.
- Затем Drive API и синхронизация с `READY`, ревизиями, атомарным обновлением, ошибками доступа.
- Работающий Engine должен зарегистрировать новую папку, не прерывая старые задания.

### Итерация 3 — генератор из словарей

- CSV/TXT/YAML, описания с корректной привязкой, случайный выбор и seed, несколько шаблонов, локали.
- Проекты получают `title/body`, генератор не знает об HTTP и сайте.
- Hot reload словарей.

### Итерация 4 — сохранение состояния и переносимость

- SQLite, контрольные точки/backup, restore, защита от дублей, запуск Windows/VPS/Colab/Molab.
- Реальный smoke test в notebook (без обязательного фонового режима).

### Итерация 5 — улучшения по результатам тестов

- Улучшение анализа двух записей, стабильная проверка результата, восстановление сломавшихся сценариев; браузерный fallback, если действительно нужен.
- Принимать решения по конкретным багам и тестам, а не умозрительным возможностям.

## 13. Критерии приёмки MVP (не заменить красивым README)

1. Recorder создаёт работоспособный декларативный проект с **обычного HTML-тестового сайта**, куда пользователь сам ввёл заголовок/текст и нажал отправку.
2. На втором локальном тестовом сайте с **обновляемым CSRF** проект правильно получает новый токен и повторно выполняет HTTP-сценарий; нельзя просто воспроизвести вчерашний POST.
3. Executor работает без запущенного браузера и действительно выполняет HTTP replay на тестовых сайтах; проверяет публикацию по подтверждению, не только статус-коду.
4. Добавление папки с проектом к запущенному Engine (сначала локально, затем на Google Drive) обнаруживается **без перезапуска** и не ломает текущие проекты.
5. Добавление строк в словари и обновление шаблонов начинает влиять на новые генерации без перезапуска.
6. При перезапуске сохраняются результаты и не повторяются уже отмеченные успешными задания; неизвестные исходы явно выделены.
7. Исполнитель не передаёт cookies на хосты вне `allowed_hosts`; диагностические файлы по умолчанию не содержат секретов.
8. Есть **одна команда** установки зависимостей и **понятная команда** запуска для разработчика, автотесты проходят.
9. Есть демонстрация полного пути «запись → проект → hot load → словари → HTTP → проверенный результат» на контролируемом тестовом ресурсе.
10. Документация честно перечисляет сайты/сценарии, для которых автоматически создать HTTP-проект не удалось.

## 15. Приложенные исходные примеры и их роль

В каталоге `references/` лежат пять предоставленных пользователем текстов чужих форумных публикаций (`1.txt` ... `5.txt`). **Они являются примерами структуры текстовой генерации, а не готовыми сценариями автопостинга и не достоверными медицинскими материалами.**

По пяти примерам видно повторяющиеся структурные блоки: заголовок с названием продукта и поисковыми вариантами, краткое вступление, ссылка, метаданные продукта, списки типовых фраз, привязанное описание, дополнительные запросы, списки географии. Реальную систему делать **обобщённой и своей**: отдельные данные и шаблоны вместо попытки полностью копировать тексты/формулировки.

Ниже три документа для передачи в работу:

- `TECH_SPEC_RU.md` — это ТЗ;
- `CODEX_START_PROMPT_RU.txt` — короткое стартовое поручение;
- `README_PACKAGE.md` — порядок передачи и тестирования.

**Итог:** нужен рабочий инструмент, который можно запустить и критиковать по факту, а не очередное обсуждение будущего инструмента.
