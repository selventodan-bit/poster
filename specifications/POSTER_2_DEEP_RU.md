## 0. КРИТИЧЕСКИ ВАЖНО: ПРОЧИТАЙ ПЕРЕД РАБОТОЙ

Продолжи разработку существующего Poster 2.0.

Репозиторий: https://github.com/selventodan-bit/poster

Рабочая ветка: `codex/poster-2-recognition`

Существующий PR: https://github.com/selventodan-bit/poster/pull/2

**Работай в этой же ветке и обновляй PR №2. Не создавай новый PR и не выполняй merge в main.**

Предыдущая реализация является хорошей архитектурной основой, но пока недостаточно универсальна.

**Не требуется очередной небольшой MVP, демонстрация на семи специально подготовленных формах или косметическое увеличение количества поддерживаемых кнопок.**

Задача — серьёзно развить универсальный механизм распознавания сайтов, обучения и создания HTTP-сценариев.

Цель продукта:

**Максимально высокая практически достижимая степень автоматического распознавания форм публикации на незнакомых форумах и сайтах, с накоплением и повторным использованием полученных знаний.**

Приоритеты:

1. Реальная универсальность и переносимость.
2. Надёжность распознавания неизвестных сайтов.
3. Полноценная система накопления знаний.
4. Автоматическая адаптация к отличиям форумов.
5. Надёжное создание HTTP-сценариев.
6. Проверяемое подтверждение публикации.
7. Удобный интерфейс с минимальным участием пользователя.
8. Совместимость с существующим Poster и HTTP Engine.

Не заявляй абсолютную универсальность или поддержку движков, которая фактически не проверена.

Однако не используй невозможность стопроцентного распознавания как повод ограничиться текущим MVP.

## 1. ОСНОВНАЯ ПРОБЛЕМА СЕЙЧАС

В предыдущем PR реализованы:

- EngineDetector.
- UniversalFormDetector.
- NetworkAnalyzer.
- HTTPWorkflowLearner.
- KnowledgeBase.
- RecognitionSession.
- Новый GUI Recorder.
- Локальные E2E-тесты.

Но существенная часть распознавания основана на простых эвристиках.

Например, в `poster/recognition/service.py` открытие формы зависит от регулярного выражения `OPEN_FORM`.

На реальном испанском форуме кнопка называется `Nuevo debate`.

Но на других форумах она может называться:

- New Topic.
- New Thread.
- Create Discussion.
- Nueva discusión.
- Nouveau sujet.
- Neues Thema.
- Новая тема.
- Створити тему.
- Nuovo argomento.
- Criar tópico.

Или вообще обозначаться иконкой без текста.

**Нельзя решать эту проблему только расширением регулярного выражения.**

Необходимо обнаруживать назначение элементов по совокупности независимых признаков.

Аналогичный недостаток присутствует в текущей KnowledgeBase.

В `poster/recognition/knowledge.py` глобальное правило в основном хранит:

- Тип редактора.
- Набор распознанных ролей.
- Позицию текстового поля.
- Простую статистику.

Это недостаточно для конечной цели.

Нам нужна обобщаемая библиотека знаний о формах, навигации, движках, действиях, сетевых сценариях, токенах и подтверждении результатов.

# ЧАСТЬ I. УНИВЕРСАЛЬНОЕ РАСПОЗНАВАНИЕ

## 2. Переработать EngineDetector

Доработай `poster/recognition/detector.py`.

Распознавание движка должно учитывать не только регулярные выражения в HTML.

Разработай многофакторный механизм, учитывающий:

- HTML meta generator.
- DOM-структуру.
- Имена классов.
- HTML-атрибуты.
- URL-паттерны.
- Ссылки на CSS и JavaScript.
- Структуру страниц.
- Наличие характерных API.
- Паттерны форм.
- Поведение JavaScript.
- Сетевые признаки.
- Известные особенности версий движков.

Один признак не должен считаться достаточным доказательством.

Предусмотри возможность одновременного обнаружения нескольких технологий, например WordPress + wpForo.

Раздели распознавание платформы, форумного компонента, версии и конкретной формы.

Введи систему версионированных адаптеров.

Целевые семейства:

- XenForo.
- phpBB.
- vBulletin.
- MyBB.
- Discourse.
- SMF.
- Invision Community.
- Flarum.
- WordPress / wpForo.
- Другие расширяемые адаптеры.

Адаптер может иметь разные уровни готовности: идентификация, обнаружение формы, проверенная публикация, проверенный HTTP-сценарий.

Не выдавай наличие сигнатуры за полную поддержку движка.

## 3. Полностью переработать распознавание навигации

Разработай универсальный NavigationDiscovery.

Poster должен находить путь от открытой страницы форума до создания новой темы, даже если форма изначально отсутствует в DOM.

Используй совокупность:

1. Семантики элементов.
2. Accessibility tree.
3. ARIA-label, title, tooltip.
4. Контекстного расположения.
5. Типа элемента.
6. HTML-атрибутов.
7. URL-паттернов.
8. Соседних элементов.
9. Структуры навигации.
10. Локализованных текстов.
11. Динамически появляющихся элементов.
12. Доступных данных о поведении интерфейса.

Предусмотри:

- Обычные ссылки.
- Кнопки.
- Выпадающие меню.
- AJAX-модальные окна.
- Вкладки.
- SPA-навигацию.
- Иконки без текста.
- Разные языки интерфейса.
- Ситуации с несколькими кнопками.
- Формы, появляющиеся после нескольких действий.

Языковые словари нужны как вспомогательная подсистема, а не как фундамент алгоритма.

Предусмотри механизм расширения локализаций без переписывания исходного кода.

Нельзя без разрешения нажимать элементы, способные создать публикацию, изменить настройки или выполнить другую существенную операцию.

Неизвестное действие должно оцениваться как потенциально опасное до подтверждения его назначения.

## 4. Усилить UniversalFormDetector

Доработай `poster/recognition/forms.py`.

Учитывай, что реальные формы значительно разнообразнее локальных фикстур.

Поддержи обнаружение:

- HTML forms.
- JS/AJAX forms.
- Contenteditable.
- Iframe-редакторов.
- Shadow DOM, когда доступ разрешён.
- Динамически созданных форм.
- Модальных окон.
- SPA-компонентов.
- Кастомных контролов.
- Нескольких редакторов.
- Многошаговых форм.
- Полей с нестандартными именами.
- Полей без имени.
- Полей без меток.
- Скрытых параметров.
- Сложной структуры кнопок отправки.

Отдельно исследуй возможности поддержки распространённых редакторов:

- TinyMCE.
- CKEditor.
- Quill.
- ProseMirror / Tiptap.
- Summernote.
- Froala.
- Обычный contenteditable.

Создай расширяемый интерфейс EditorAdapter.

Каждый адаптер должен определять способ корректного заполнения редактора, включая необходимые события ввода и синхронизацию с состоянием приложения.

Не считай изменение видимого DOM доказательством того, что содержимое будет отправлено серверу.

## 5. Разработать многофакторное сопоставление полей

Поле заголовка нельзя определять исключительно по слову `title` или его позиции.

Используй:

- Семантическую роль.
- Атрибуты.
- Контекст.
- Расположение относительно редактора.
- Тип элемента.
- Предыдущий опыт.
- Структуру аналогичных форм.
- Связь с кнопкой публикации.
- Поведение при вводе.
- Данные успешного обучения.

При обнаружении нескольких подходящих полей система должна сохранять варианты с объяснимыми оценками.

Не выбирать неоднозначный вариант случайным образом.

Знания о ранее распознанных формах должны реально повышать способность системы разрешать такие ситуации.

# ЧАСТЬ II. ПОЛНОЦЕННАЯ БИБЛИОТЕКА ЗНАНИЙ

## 6. Кардинально расширить KnowledgeBase

Это **один из наиболее важных пунктов всего задания**.

Текущая реализация KnowledgeBase слишком примитивна.

Необходимо создать полноценную версионированную библиотеку знаний, пригодную для многократного использования на новых сайтах.

Разработай модель, которая может хранить очищенные, обобщённые и безопасные правила следующих категорий:

**EngineKnowledge**

- Признаки CMS.
- Семейство и возможная версия.
- Структурные особенности.
- Типичные маршруты.
- Доступные адаптеры.

**NavigationKnowledge**

- Паттерны поиска создания темы.
- Типы элементов.
- Последовательность безопасных навигационных действий.
- Признаки открытия нужной формы.

**FormKnowledge**

- Структура формы.
- Семантические роли.
- Связи между полями.
- Тип редактора.
- Устойчивые структурные паттерны.
- Варианты оформления.
- Типичные дополнительные параметры.

**SubmissionKnowledge**

- Типы HTTP-запросов.
- Схемы тел запросов.
- Последовательности операций.
- Зависимости между запросами.
- Признаки успешной отправки.
- Обобщённые маршруты API.

**TokenKnowledge**

- Названия и роли динамических параметров.
- Безопасные способы получения свежих значений.
- Источники из HTML/JSON/заголовков.
- Зависимости и срок действия, если установлены.

**VerificationKnowledge**

- Структуры подтверждения публикации.
- Признаки постоянных ссылок.
- Способы проверки заголовка и текста.
- Известные варианты ошибок.

Сохранять **шаблоны и способы получения значений**, а не реальные секретные значения.

Пароли, cookies, индивидуальные токены, персональные данные и тексты сообщений не должны попадать в общую библиотеку.

## 7. Повторное использование знаний на других сайтах

Главная цель самообучения:

Poster обучился на форуме A.

Затем пользователь открыл форум B с похожей структурой.

Poster должен:

1. Извлечь признаки сайта B.
2. Найти похожие ранее изученные правила.
3. Сопоставить различия.
4. Определить применимые части знаний.
5. Адаптировать структуру формы.
6. Найти локальные источники параметров.
7. Построить кандидата публикации.
8. После разрешения проверить его на сайте B.
9. Сохранить полученные знания.
10. Не ухудшить ранее работавшие правила.

Нужно различать:

- Полное совпадение.
- Частичное совпадение.
- Совместимый вариант.
- Неизвестную структуру.
- Конфликтующие правила.

Добавь:

- Версионирование.
- Приоритеты правил.
- Статистику успешности.
- Учёт отрицательных результатов.
- Механизм разрешения конфликтов.
- Возможность отключить неудачное правило.
- Миграции базы.
- Резервное копирование.
- Дедупликацию.
- Регрессионные тесты.
- Экспорт и импорт безопасных правил.

**Важно: библиотека не должна просто запоминать отдельные CSS-селекторы конкретных сайтов.**

Она должна хранить обобщаемые знания и применять их к новым структурам.

## 8. Предотвратить ложное самообучение

Один удачный результат на сайте A не означает, что правило универсально.

Введи уровни зрелости правила:

- Наблюдаемое.
- Подтверждённое на одном сайте.
- Подтверждённое на нескольких независимых вариантах.
- Подтверждённое на разных установках движка.
- Регрессионно проверенное.

Не смешивай уверенность в распознавании с доказательством HTTP-публикации.

При неудачном применении правило должно получать отрицательное свидетельство.

Не допускай, чтобы ошибочное правило автоматически распространялось на все сайты.

# ЧАСТЬ III. HTTP-РАСПОЗНАВАНИЕ И АДАПТАЦИЯ

## 9. Углубить NetworkAnalyzer

Проведи аудит `poster/recognition/network.py`, `poster/recorder/capture.py` и `poster/recognition/learner.py`.

Обязательно поддержи:

- URL-encoded.
- JSON.
- Text multipart.
- Вложенные объекты.
- Массивы.
- HTML-escaped значения.
- Unicode.
- Разные кодировки, когда их можно определить.
- Отдельные запросы заголовка и текста.
- Создание черновика.
- Последующую публикацию черновика.
- Зависимости между запросами.
- Редиректы.
- AJAX-ответы.
- Неоднозначные последовательности.

Обнаружь и исправь проблемы корреляции.

В существующей реализации используется изменяемый общий `capture.action_id`.

Асинхронные ответы могут приходить позже начала следующего действия. Поэтому принадлежность ответа к действию нельзя определять только по текущему глобальному состоянию.

Фиксируй причинную связь на уровне конкретного запроса, его идентификатора, инициатора, действия и ответа.

Не выводи зависимость исключительно из близости по времени.

## 10. Улучшить HTTPWorkflowLearner

Сценарии должны строиться из реально наблюдавшихся данных.

Особое внимание:

- Динамические CSRF-токены.
- Nonce.
- Данные из meta.
- Hidden inputs.
- JSON responses.
- Идентификаторы черновиков.
- Дополнительные API-вызовы.
- Вложенные зависимости.
- Заголовки запросов.
- Cookie-based authentication.
- Сессионные параметры.
- HTML/JSON escaping.
- Текстовые multipart-формы.

Источники динамических значений должны вычисляться при каждом выполнении, если этого требует сервер.

Нельзя заменять неизвестные параметры постоянными значениями из записи.

Если невозможно объяснить происхождение критического параметра, сценарий остаётся непроверенным.

Нельзя создавать ложный статус HTTP_READY.

## 11. Надёжная проверка результата

Переработай механизм подтверждения.

Текущего фиксированного тайм-аута в четыре секунды недостаточно.

Реальные сайты могут отвечать медленно, публиковать асинхронно или задерживать обновление страницы.

Реализуй:

- Настраиваемые тайм-ауты.
- Ожидание конкретных событий.
- Отслеживание завершения публикации.
- Ограниченные read-only проверки.
- Проверку постоянной ссылки.
- Проверку заголовка и текста.
- Обработку перенаправлений.
- Различение ошибки и неопределённого результата.

Должны существовать разные результаты:

- Публикация подтверждена.
- Публикация отклонена.
- Авторизация истекла.
- Результат неизвестен.
- Ссылка не обнаружена.
- HTTP-сценарий не построен.
- Требуется ручное обучение.

Нельзя выполнять повторную отправку после неоднозначного результата.

Второй HTTP-тест должен использовать отличающийся тестовый контент, чтобы избежать конфликта с проверкой дублей. Он выполняется исключительно после отдельного согласия пользователя.

# ЧАСТЬ IV. БРАУЗЕР, АВТОРИЗАЦИЯ И БЕЗОПАСНОСТЬ

## 12. Исправить работу с внешними ресурсами

В `RecognitionSession.gate()` текущая блокировка всех сторонних доменов способна нарушать работу обычных сайтов, использующих CDN.

Раздели:

- Загрузку безопасных статических ресурсов.
- Разрешённую навигацию.
- Авторизационные переходы.
- Отправку данных.
- Сторонние запросы, требующие отдельного разрешения.

Разработай ограниченную политику разрешённых read-only ресурсов без автоматической передачи секретов третьим сторонам.

Сохрани жёсткий контроль мутаций, адресов отправки и доменов.

Не открывай произвольный доступ к сторонним ресурсам ради повышения распознавания.

Не реализовывай обход CAPTCHA, антибот-защит, ограничений доступа или модерации.

## 13. Исправить обработку авторизации

Авторизация не всегда определяется наличием поля пароля.

Учитывай:

- Уже авторизованную сессию.
- Страницы входа.
- AJAX-авторизацию.
- Редиректы к входу.
- HTTP 401/403.
- Истечение cookies.
- Защищённые разделы форума.
- Разные состояния для гостей и пользователей.

Сохраняй авторизацию только индивидуально для проекта.

Проверь совместимость с прежним `POSTER_SESSION_KEY` и старыми `session.enc`.

На Windows уже применялось хранение ключа по пути `$HOME\.poster\session.key`. Новая версия использует другой локальный механизм.

Обеспечь безопасное использование или перенос прежнего ключа, не перезаписывая его и не делая ранее созданные проекты недоступными.

Не печатай ключи в журнал и не сохраняй их в общую библиотеку знаний.

## 14. Изоляция отправок

После разрешения одной публикации браузер должен выполнять только необходимые операции в пределах разрешённого сценария.

Избегай ситуации, когда временное снятие read-only ограничения позволяет стороннему JavaScript выполнять непредусмотренные изменяющие запросы.

Сохраняй контроль над количеством публикаций и предотвращение повторов.

# ЧАСТЬ V. ИНТЕРФЕЙС

## 15. Recorder должен работать практически автоматически

Основной сценарий пользователя:

1. Вставил URL.
2. Ввёл заголовок.
3. Ввёл текст.
4. Нажал «Распознать сайт».
5. Посмотрел, что найдено.
6. Разрешил тестовую публикацию.
7. Получил подтверждённый результат.
8. Разрешил отдельную HTTP-проверку.
9. Получил готовый сохранённый проект.

Если распознавание не удалось — используется ручное обучение.

Не заставляй пользователя:

- Перепечатывать маркеры.
- Вводить CSS-селекторы.

- Редактировать YAML.
- Искать токены.

После успешной HTTP-проверки должна быть возможность автоматического сохранения готового проекта в предварительно выбранную папку.

Раздели основной интерфейс и расширенную диагностику.

Улучши сообщения об ошибках: пользователь должен понимать конкретную проблему.

Перед тем как просить пользователя проверять программу на реальных форумах, должны быть выполнены следующие условия.

**Универсальное распознавание:**

- Не зависит от конкретного языка кнопок.
- Работает с разными структурами.
- Поддерживает несколько типов редакторов.
- Умеет искать форму через безопасную навигацию.
- Корректно распознаёт неоднозначные случаи.

**Библиотека знаний:**

- Хранит полезные обобщённые правила.
- Сохраняется между запусками.
- Переносит знания между независимыми сайтами.
- Умеет адаптировать правила.
- Не хранит секреты.
- Учитывает неудачные применения.
- Имеет регрессионные проверки.

**HTTP-обучение:**

- Поддерживает несколько форматов передачи.
- Обрабатывает проверяемые последовательности запросов.
- Работает с динамическими параметрами, источник которых установлен.
- Не создаёт ложных HTTP_READY.
- Подтверждает публикацию независимо.
- Не повторяет неоднозначные отправки.

**Интерфейс:**

- Нормально запускается.
- Не требует маркеров.
- Не требует ручных CSS.
- Показывает понятную диагностику.
- Предусматривает остановку операций.
- Сохраняет готовый проект.
- Не теряет существующие ключи и сессии.

**Автоматические испытания:**

- Старые тесты проходят.
- Новые тесты проходят.
- Регрессионные тесты проходят.
- Независимые контрольные формы проверены.
- Известные ограничения документированы.

Не объявляй универсальность доказанной исключительно по локальным фикстурам.
